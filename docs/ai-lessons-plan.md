# AI lessons: plan and decisions

This is JC's brief of 2026-11-06. It replaces the lessons embedded in map files with on-demand,
30-minute lessons generated by Claude and cached locally. The existing reviewed lessons are
archived, never deleted. The work is on branch `ai-lessons`, committed per phase and not pushed.
The phase checkboxes are in `Tasks/TASKS.md`.

## What the code does today (read before writing)

- **Embedded lessons.** 350 nodes carry two fields: `lesson` (explanation, worked example,
  practice, boundary case, references and more) and `lessonCard` (edition, demonstration,
  assessment contract, practice mode and more).
  - The same 350 are byte-identical in `Maps/Humanoid-Helix-Atlas.json`,
    `Maps/Humanoid Protocol Droid Helix.json` and `Maps/Robotics-Atlas.json`.
  - `Maps/Skill-Solar-System.json` has none.
  - Map files are written as `JSON.stringify(map, null, 2) + "\n"`.
- **Rendering.** `src/lesson.js` turns `node.lesson` and `node.lessonCard` into card sections
  (`lessonSections`, `contentStatusLine`, `needsRealEvidence`, …). `src/app.js` renders them inside
  the details dialog (`fillDetails`). The inspector card shows chips, the description, buttons, the
  mini graph and the proficiency controls.
- **Other readers.** The guided review (`src/review.js`, `src/review-dialog.js`) does not read
  lessons. The Guide's `get_skill` tool reads `hasLesson`.
- **Proficiency** is `node.proficiency80` plus the shared record (`desktop/proficiency-store.cjs`),
  and it is written only by the user's Yes, No or Clear.
- **The Claude integration** (`desktop/guide.cjs`) runs in the main process with
  `@anthropic-ai/sdk` 1.6.0. The key is stored with Electron `safeStorage` in
  `userData/guide/api-key.bin`, or read from `ANTHROPIC_API_KEY`. The page has no network access
  (`connect-src 'none'`, every request blocked) and never sees the key. The lessons reuse the
  same key and the same client factory.
- **userData** is `%APPDATA%\skill-solar-system` in development.

## Docs checked (platform.claude.com, 2026-11-06)

- **Structured output.** It is requested with `output_config: { format: { type: "json_schema",
  schema } }` and needs no beta header. It works with streaming, and the JSON arrives as text
  deltas.
  - Every object needs `additionalProperties: false`.
  - `minItems` may only be 0 or 1. `maxItems` is not listed as supported, and string or number
    bounds are not supported.
  - Up to 24 optional parameters and 16 union-typed ones are allowed per request.
  - **Decision:** every field is required. Nullable fields are kept to the two that need it
    (`safety`, `demonstration`). Counts such as "3–5 problems" are checked locally, after parsing.
- **Forced `tool_choice` is a 400 on Sonnet 5.5 and Opus 5.5,** so structured output is used
  instead of a forced tool.
- **Model ids:** `claude-haiku-5-5`, `claude-sonnet-5-5` and `claude-opus-5-5`. The default is
  `claude-sonnet-5-5`, as the brief asks.
  - Adaptive thinking is the model default, and effort is set to `medium`.
  - Server-side refusal fallback (`fallbacks: "default"`) is on for Sonnet and Opus. Haiku 5.5 has
    no server-side fallback.
- **Prices in US$ per million tokens.** They go in `config/claude-pricing.json`, dated 2026-11-06.

  | Model | Input | Cache write (5 min) | Cache read | Output |
  | --- | --- | --- | --- | --- |
  | Haiku 5.5, prompt ≤100k | 0.10 | 0.125 | 0.01 | 0.50 |
  | Haiku 5.5, prompt >100k | 0.50 | — | — | 2.50 |
  | Sonnet 5.5 | 2 | 2.50 | 0.10 | 10 |
  | Opus 5.5 | 4 | 5 | 0.20 | 20 |

## Design

### Phase 1: Lesson store and migration

- **Where lessons live:** `userData/lessons/<mapKey>/<readable-id>-<sha12>.json`, one per node.
  - `mapKey` is the atlas family (`humanoid-helix-v1`, `sss-robotics-foundations-2026-09`), else
    the dataset key, else `default`. Sub-maps of one family therefore share lessons.
  - File names use the same readable-plus-hash scheme as the proficiency store, because node ids
    contain `:`.
- **Record:**

  ```
  { format: "helixskill-lesson", version: 1, nodeId, mapKey, source, status, promptVersion, model,
    createdAt, inputHash, tokensIn, tokensOut, content, userNotes, verification }
  ```

  - `source` is `reviewed-archive` or `ai-generated`. `status` is `reviewed`, `unreviewed` or
    `flagged`.
  - For an archive, `content` is `{ lesson, lessonCard }`, copied verbatim.
  - A node has at most one archive and one AI lesson. They are stored as `<id>.archive.json` and
    `<id>.ai.json`, so regenerating can never overwrite an archive.
- **Migration** is `scripts/migrate-lessons-to-store.mjs`. It defaults to a dry run; `--apply`
  writes.
  - It first takes a one-time backup of every top-level `Maps/*.json` file into
    `backups/pre-ai-lessons/`, with `SHA256SUMS`, once only.
  - It writes the archive records, then removes `lesson` and `lessonCard` from each map.
  - Every other byte of the map stays as it was: the files are re-serialised in their own format,
    and node key order is kept.
  - A manifest (`backups/pre-ai-lessons/manifest.json`) records, for each map, the hashes before
    and after and each removed key's position in its node.
- **Checks.** The count moved equals the number of nodes that had lessons. Every archive
  re-serialises identically. Node and edge counts, ids, positions, levels and proficiency values
  are unchanged.
- **Restore** is `scripts/restore-lessons.mjs`. It puts the fields back at their recorded
  positions, and the result must hash to the "before" value, which is checked.
- **Reading.** Everything reads through `getLesson(nodeId)`: the page asks the main process. A
  map that still embeds lessons (an older file, or a rebuild) keeps working: `getLesson` falls back
  to the embedded fields, shown as a reviewed archive.
- **Only the top-level maps** in `Maps/` are migrated. `Maps/Archived maps`, `Maps/Backups` and
  the other sub-folders are archives and are left as they are. The script accepts other paths
  explicitly.

### Phase 2: One skill card

- `src/skill-card.js` is used by the inspector and the details dialog, for every node of every map.
- **The card shows:**
  - the name;
  - chips for course, subject (`subdomain`), helix level, build stage, tier (Core, Working or
    Specialist), and type (QUANT or QUAL);
  - the one-sentence description;
  - prerequisites with proficiency colours, and Unlocks, both clickable;
  - a lesson status badge;
  - the primary button and a small Regenerate action;
  - the proficiency controls.
- **The lesson body is no longer on the card.** The old lesson-on-card rendering (the
  `lessonSections` sections in `fillDetails`) is removed.
- **Milestones and checkpoints** show a demonstration checklist built from their prerequisites,
  with proficiency marks, instead of a lesson button.

### Phase 3: Generation (main process, `desktop/lessons.cjs`)

- **Context per skill**, built in the page from the map and sent as data:
  - the skill: name, description, course, subject, level, stage, tier, type, practice, assessment
    mode;
  - its immediate prerequisites, with descriptions and a proficient flag;
  - what it unlocks (names only);
  - the learner profile from Settings.
- `inputHash` is the sha256 of that context, without the learner profile.
- **Type** is `helixType` when present, else derived from the assessment mode ("written
  calculation" or "calculation and explanation" means QUANT), else QUAL.
- **Practice** is `helixPractice`, else derived from `lessonCard.practiceMode`, else `written`.
- **Prompt.** A stable system prompt, cached with `cache_control`, plus one user message with the
  context as JSON. Structured output follows the lesson schema, streamed. Progress is reported
  section by section, from the top-level keys seen in the partial JSON.
- **Local validation** after parsing:
  - section counts: 2–4 objectives, 2–3 guided problems, 3–5 independent problems, 3 checks;
  - `safety` is required for hands-on, electrical, battery, power-tool, welding or chemical
    topics;
  - `demonstration` is required for hands-on skills, with `satisfiedByLesson: false`.

  A lesson that fails is retried once, then fails with a clear message and nothing is saved.
- **Verification for QUANT skills:**
  - A second request re-solves every guided and independent problem from the statement alone,
    without the key.
  - Answers are compared locally where both sides give a numeric `finalValue`, within 2% (unit
    names compared loosely).
  - A problem that disagrees is regenerated once and re-checked. If it still disagrees, the lesson
    is saved with status `flagged` and the disagreeing problems are listed.
  - Problems without a numeric value are reported as "not checked automatically".
- **Errors.** Rate limits, 5xx errors, timeouts and invalid JSON get one automatic retry, then a
  clear message. A cancel aborts the stream. Nothing partial is ever saved.
- **Caching.** A lesson is generated once. A newer prompt version marks it "Update available" and
  never replaces it automatically.

### Phase 4: Viewer

- A lesson dialog shows the sections:
  - math in `$…$` and `$$…$$`, rendered with KaTeX, bundled offline;
  - code blocks;
  - solutions behind "Show answer".
- **AI lessons** carry the badge "AI-generated · not yet reviewed" and have **Mark reviewed**,
  **Flag a problem** (with a note) and **Regenerate** buttons.
- **Archives** render in the same viewer, with their own sections.
- **Review sessions** show the cached lesson's practice questions for the skill being reviewed,
  so the same questions recur. Answers stay manual.

### Phase 5: Settings, cost and batch

- **Settings:**
  - model;
  - learner profile;
  - a monthly cap for lessons, $20 by default, separate from the Guide's $10;
  - "Ask before generating".
- **Usage:** lessons generated, tokens in and out, and the estimated cost this month, priced from
  `config/claude-pricing.json`.
- **Pre-generate next up:** a background queue for the next N frontier skills (10 by default),
  one at a time. It respects the cap and can be paused.
- **Export and import** the store as a zip. The zip is written and read in the main process with
  Node's zlib (deflate), so no new dependency is needed.

## Decisions logged

1. **The Guide and lessons share the key and the client,** but have separate monthly caps: $10
   for the Guide and $20 for lessons.
2. **One archive per node and family.** The three maps hold identical lessons, so two families
   give 700 archive records: 350 per family.
3. **Archived and backup map folders are not migrated.**
4. **Embedded lessons in a map that is opened still display,** as an archive, through
   `getLesson`, so nothing is lost if a map is rebuilt with lessons.
5. **AI practice is never evidence.** The viewer and the demonstration section say "not satisfied
   by this lesson", and no code path from lessons writes proficiency.
6. **The real end-to-end run on three skills needs an API key on this computer.** There is none
   today, so it is reported as pending if it can't be run.

## Results

### Migration (2026-11-06)

- **Dry run**, then `--apply`, on the four top-level maps. The backup is
  `backups/pre-ai-lessons/`: 4 maps with `SHA256SUMS`, plus `manifest.json`.

  | Map | Nodes | Edges | Lessons moved | Graph and answers |
  | --- | --- | --- | --- | --- |
  | Humanoid Protocol Droid Helix.json | 3,422 | 11,281 | 350 | unchanged |
  | Humanoid-Helix-Atlas.json | 3,696 | 12,138 | 350 | unchanged |
  | Robotics-Atlas.json | 1,955 | 5,783 | 350 | unchanged |
  | Skill-Solar-System.json | 1,769 | 5,142 | 0 (left byte-identical) | unchanged |

- **Archives:** the 1,050 removed lessons are stored as 700 archive records, 350 for
  `humanoid-helix-v1` and 350 for `sss-robotics-foundations-2026-09`. The two helix maps share a
  family, and their lessons were byte-identical. Every archive re-serialises identically.
- **Graph and answers:** compared with the backup, every map has the same node and edge counts and
  the same node ids, positions, levels, courses and other fields, the same edges, and the same
  `proficiency80` values. Only `lesson` and `lessonCard` are gone.
- **Restore test.** `node scripts/restore-lessons.mjs` reports for all three maps "350 lessons would
  be restored; byte-identical to the pre-migration file". The round trip is also covered by
  `tests/lesson-migration.test.mjs`, applied on fixtures.

### Real run (Claude Haiku 5.5, the cheapest model)

Run with `npx electron scripts/real-lesson-run.cjs` using the key the app saved. The records,
including the context each lesson was written from, are in `docs/samples/`, and the summary is in
`docs/samples/run-summary.json`.

| Skill | Type | Time | Tokens in / out | Est. cost | Answer check |
| --- | --- | --- | --- | --- | --- |
| Boolean algebra (`m-boolean`) | MTH QUANT | 29.5 s | 3,786 / 4,756 | $0.0029 | 0 of 8 checkable (answers are not single numbers) |
| Right-triangle trigonometry (`m-trig`) | MTH QUANT | 27.1 s | 5,180 / 6,638 | $0.0040 | 8 of 8 agree |
| Solder through-hole components (`hx-elx-soldering-tht`) | ELX hands-on | 32.0 s | 3,009 / 6,010 | $0.0034 | not QUANT; safety and demonstration present |
| Set up a Python ML environment (`hx-ai-python-ml-env`) | AIL QUAL | 31.4 s | 3,068 / 6,027 | $0.0034 | not QUANT |

- **Validation:** all four passed local validation first time; there were no retries or repairs.
  The `m-trig` independent-practice answers were spot-checked by hand and are correct:
  - 12/13 = 0.9231;
  - 9 tan 40° = 7.552 m;
  - 12 sin 15° = 3.106 m;
  - 4/sin 25° = 9.465 m;
  - 5/8 = 0.625.
- **Cost on Sonnet 5.5 (estimate only):** at its prices ($2 in, $10 out per million tokens), the same
  lessons would cost roughly $0.05–0.08 each, and Opus 5.5 about twice that. Sonnet itself was not
  run.
