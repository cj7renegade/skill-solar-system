# Robotics learning editions 01, 02 and 03 — integration summary

Return note for the next authoring edition, answering the handoffs in
`packages/shared-foundations-learning-edition-01/INTEGRATION.md`,
`packages/controlled-joint-learning-edition-02/INTEGRATION.md` and
`packages/complete-arm-learning-edition-03/INTEGRATION.md`.

## Dataset identity and ID mapping

The content was applied to the **dedicated robotics v3 map only**. The original Skill Solar System
atlas was not opened for writing, not patched, and not read for answers.

| | |
| --- | --- |
| Target map | `Maps/Robotics-v3/Robotics-v3-Lessons.json` (381 entries, 894 connections: 888 required, 6 supporting) |
| First built from | `Maps/Robotics-v3/Robotics-v3-Preview.json`, generated by `authoring/robotics-v3/build-preview.mjs` from the reviewed v3 specification. Later runs patch the export in place, so any newer change to it is carried forward |
| Atlas family | `robotics-foundations-integration-v3-review`, unchanged by every import |
| Review identity | `metadata.datasetKey = robotics-curriculum-v3` (see “Title and review sessions”) |
| Runtime identity | `rob3:<planning-id>`, exactly the `proposed_runtime_id` each lesson carries. Confirmed against the map, not assumed |
| Original atlas family | `sss-robotics-foundations-2026-09`, a different family, so no answer can cross between them |

Identity is checked per lesson rather than taken on trust: planning id, runtime id, name, required
prerequisites and the `node_contract_sha256` fingerprint must all agree with the reviewed
specification before a lesson is applied. The fingerprint is reproduced byte for byte from Python's
`json.dumps(..., sort_keys=True)`, spacing and `\uXXXX` escapes included (`pythonJson` in
`authoring/robotics-v3/lessons.mjs`).

## Field mapping

The verbatim lesson record is stored on each node as `lesson`, so every authored field travels with
the export, including the ones the interface does not render yet (`branch`, `dependency_depth`,
`node_contract_sha256`, `content_status`, `proficiency_write`). A reader-facing summary is stored as
`lessonCard`, and the two card fields the app already had are filled from the lesson:

| Lesson field | Where it goes |
| --- | --- |
| `details` | `node.details` — the explanation and worked example, two paragraphs |
| `placement_note` | `node.placementNote` |
| `explanation`, `worked_example` | card section “Explanation and worked example” |
| `why_it_matters` | card section “Why this matters and what it builds on”, beside prerequisites read from the map's own edges |
| `practice` | card section “Practice question”, answer behind **Show answer** |
| `boundary_case` | card section “Boundary or misconception check”, answer behind its own **Show answer** |
| `full_demonstration`, `assessment_contract` | card section “Full demonstration and evidence”, rendered as labelled text |
| `references`, `required_future_work` | card section “References and remaining learning work” |
| `practice_mode`, `assessment_contract.mode` | named in the card, distinguishing an introductory exercise from a simulated result and from physical or deployed-system work |
| `instructional_scope` | shown once under the card's status lines |
| everything else | kept verbatim in `node.lesson` |

Edition 03 uses the same schema as edition 02, so it needed no new mapping. Its `practice_mode`
wording differs (“physical or deployed-system evidence” rather than “target-device”), and the card
recognises both, because whether real hardware is still required is the part a reader must not
misread.

Edition 01 predates the per-lesson `full_demonstration` and `assessment_contract` fields. Both were
taken from the reviewed specification, which editions 02 and 03 copy verbatim (checked). No
demonstration text was invented. `assessment_contract.task` repeats the demonstration wording in all
254 entries, so the card shows it once rather than twice.

## The two issues the edition 03 handoff raised

**Title and review sessions — fixed, not deferred.** The previous summary reported that changing the
map title restarted title-keyed guided-review sessions. Review identity no longer depends on the
title:

- A map may declare `metadata.datasetKey`. `mapKey()` uses it when present, and the title otherwise,
  so every map written before this field behaves exactly as it did.
- A session saved before the key existed is found by its node set and re-stamped under the new key;
  the old entry is replaced rather than left behind. Queue, position, visited list, skipped list and
  answers all carry over.
- A map that declares a key still does **not** adopt a session from a different node set.
- The import declares `datasetKey = robotics-curriculum-v3` and restates the counts in the title in
  the same run. The migration is checked on the real 381-entry map by the importer itself
  (`preservation.reviewSessionsPreserved`), in unit tests, and in the Electron app: a session saved
  under the old title `Robotics curriculum v3 — 193 introductory lessons, 187 pending` is planted in
  the app's own review store, the imported map is opened, and **Resume review** offers the same
  skill at the same position with the same skipped list.

No old count remains in the title: it reads *Robotics curriculum v3 — 254 introductory lessons, 126
pending*. Review *order* is unchanged throughout — it comes from saved heights, names and ids, none
of which any import touches.

**Content labels — fixed.** Every entry previously carried one planning-era `lessonStatus`
(“scope and assessment specified; full lesson authoring pending”), including the 254 that now have a
card and the roadmap note. Each entry's `lessonStatus` is now restated to match what it actually has:

| Entry | `contentStatus` | `lessonStatus` |
| --- | --- | --- |
| 254 authored | `introductory lesson authored` | `introductory lesson available; extended lesson and further practice authoring pending` |
| 126 pending | `introductory lesson pending` | `scope and assessment specified; introductory lesson not yet authored` |
| 1 roadmap | `roadmap note, not assessed` | `roadmap note; not assessed, and no lesson is planned for it` |

The card reads both: a first line saying which edition wrote the card, a second saying that extended
lessons and further practice are still to be authored, and then the lesson's own
`instructional_scope`. An entry with no card says “No introductory lesson for this entry yet” and
offers no empty sections. The roadmap note says “Roadmap note — not an assessed entry, and no lesson
is planned for it”, has no lesson sections, and is `assessable: false`.

## Limitations

- These are introductory cards. They are not a complete course, an exhaustive question bank, or
  evidence of practical mastery. **Extended lesson and practice authoring is still pending for every
  entry, including all 254 that have a card.**
- 126 assessable entries still have no introductory lesson. One roadmap entry is not assessed.
- Full introductory coverage of the I02 chain is a content fact. It says nothing about what the
  learner can do, and the physical arm milestone remains unverified. Physical grasping, loaded
  motion, stopping and calibration are still real demonstration requirements.
- Nothing in the application writes a proficiency answer by itself. Opening a card, following a
  prerequisite link, revealing an answer, reading an exercise or resuming a review changes nothing;
  the app has no “mark exercise complete” control to attach an answer to, and none was added. Only
  the existing Yes / No / Clear controls and the guided review write answers.
- The teaching labs (`joint_lab.py`, `arm_lab.py`) stay optional offline material. Neither is wired
  to the app. The edition 03 lab needs NumPy, models planar kinematics only, is not a full dynamic
  simulator or a general six-dimensional IK solver, and has no hardware interface. Do not connect it
  to actuators.
- The export is 2.5 MB. It opens well within the app's 10 MB limit, and Save, reopen and the draft
  cache were all exercised at that size.
- Review-session migration was verified for this map's own case: a session saved under the old title
  over the same 381 nodes. A session saved over a *different* node set is still correctly refused,
  which is the intended behaviour but means an old session for a map that has since gained or lost
  nodes is not recovered.
- Not tested: hardware, wiring, firmware, physical measurement, or any claim that a learner has
  demonstrated anything. Content status is not proficiency.
- Pre-existing and unrelated: `node tests/review-e2e.mjs` with `SSS_ATLAS` set times out when it
  opens the 5.4 MB atlas at the end of its long session. The same file opens correctly in a fresh
  session, and the failure reproduces on the commit before this work began.
